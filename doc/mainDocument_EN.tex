\section{Analysis of the Three Reported Defects}\label{sec:motivation}

\subsection{Option Monad: \texttt{pure} Does Not Satisfy the Right-Identity Law}\label{sec:bug1}

The \texttt{Option} monad is expected to satisfy the monad laws for \emph{every} value its type parameter can hold, including \texttt{bool}. The original implementation of \texttt{Option::pure} was:

\begin{lstlisting}[caption={Original \texttt{Option::pure} (src/CategoryTheory.php)}]
public static function pure(mixed $value): self {
    return ($value === null || $value === false)
        ? new None()
        : new Some($value);
}
\end{lstlisting}

Taking $m = \mathtt{Some(false)}$ and $f = \texttt{Option::pure}$, the right-identity law $m \mathbin{>\!\!>\!\!=} \texttt{pure} \equiv m$ requires $m\mathbin{>\!\!>\!\!=}f$ to equal \texttt{Some(false)}. Instead it produced \texttt{None}, because \texttt{pure} conflated the domain value \texttt{false} with the \emph{absence} of a value — exactly the distinction the \texttt{Option} monad exists to preserve. The root cause is that \texttt{null} (absence) and \texttt{false} (a legitimate boolean payload) are not the same value, yet the guard treated them identically.

\textbf{Fix.} Only \texttt{null} denotes absence:
\begin{lstlisting}[caption={Fixed \texttt{Option::pure}}]
public static function pure(mixed $value): self {
    return ($value === null) ? new None() : new Some($value);
}
\end{lstlisting}

\textbf{Correctness argument.} For any $v \neq \mathrm{null}$, $\mathrm{pure}(v) = \mathrm{Some}(v)$ and $\mathrm{Some}(v)\mathbin{>\!\!>\!\!=}\mathrm{pure} = \mathrm{pure}(v) = \mathrm{Some}(v)$ by the definition of \texttt{Some::bind}, so right identity holds for every non-null value, including \texttt{false} -- the one case the original code broke. For $v=\mathrm{null}$, $\mathrm{pure}(\mathrm{null})=\mathrm{None}$ and $\mathrm{None}\mathbin{>\!\!>\!\!=}f=\mathrm{None}$ for any $f$ by \texttt{None::bind}, so the law holds there too. The fix restores the law for the entire domain, not just the reported counter-example.

One caller, \texttt{fetchLiveJsonOption()} in \texttt{index.php}, had silently relied on the old double meaning: \texttt{file\_get\_contents()} returns the sentinel \texttt{false} on failure, and the code built an \texttt{Option} from it via \texttt{Option::pure(\$raw)}. Since \texttt{pure} no longer treats \texttt{false} as absence, that call site was changed to test the sentinel explicitly instead of overloading a general-purpose constructor with a local, API-specific meaning:
\begin{lstlisting}[caption={index.php -- explicit sentinel check instead of overloaded pure()}]
$raw = @file_get_contents($url, false, $ctx);
if ($raw === false) return new None();
$decoded = json_decode($raw, true);
return $decoded === null ? new None() : new Some($decoded);
\end{lstlisting}
This call site, and every other place in the project that constructs or consumes an \texttt{Option}, is examined in full in the audit of Section~\ref{sec:audit}, and the fix is exercised against the two real external services it talks to in Section~\ref{sec:verification}.

\subsection{Monoid: \texttt{TripMetrics::append} Is Not Associative}\label{sec:bug2}

\texttt{TripMetrics} is declared a \texttt{Monoid}, which requires $(a\oplus b)\oplus c = a \oplus (b\oplus c)$ for all values, exactly. The original \texttt{append} rounded the running total to two decimals after \emph{every} addition:
\begin{lstlisting}[caption={Original \texttt{TripMetrics::append}}]
public function append(Monoid $other): self {
    return new self(
        round($this->costEur + $other->costEur, 2),
        ...
    );
}
\end{lstlisting}

For $a=0.004,\,b=0.004,\,c=0.005$ (Table~\ref{tabl:monoid}), rounding after each step amplifies the order in which values are combined into a visible difference: grouping $(a\oplus b)$ first rounds $0.008\to 0.01$, then $0.01+0.005\to 0.02$; grouping $(b\oplus c)$ first rounds $0.009\to 0.01$, then $a+0.01\to 0.01$. The two totals disagree, so the monoid is not actually associative — the repeated rounding is a lossy, order-dependent operation disguised as a pure sum.

\begin{table}[!ht]\centering
\caption{Associativity counter-example reported by Prof.~Grinis}
\label{tabl:monoid}
\begin{tabular}{|l|r|r|}\hline
Grouping & Original (buggy) & Fixed \\\hline
$(a\oplus b)\oplus c$ & 0.02 & 0.01 \\\hline
$a\oplus (b\oplus c)$ & 0.01 & 0.01 \\\hline
\end{tabular}
\end{table}

\textbf{Fix.} Round to whole cents exactly once, at construction, and keep that integer as the value actually added:
\begin{lstlisting}[caption={Fixed \texttt{TripMetrics} -- integer cents as the additive carrier}]
public readonly float $costEur;
public readonly int $costCents;

public function __construct(float $costEur, ...) {
    $this->costCents = (int) round($costEur * 100);
    $this->costEur = $this->costCents / 100;
}

public function append(Monoid $other): self {
    return new self(
        ($this->costCents + $other->costCents) / 100,
        ...
    );
}
\end{lstlisting}

\textbf{Correctness argument.} Let $c(x)$ denote the integer \texttt{costCents} stored by a \texttt{TripMetrics} value $x$, and let $x \oplus y$ denote \texttt{\$x->append(\$y)}. By construction, $c(x\oplus y) = c(x) + c(y)$ exactly, because \texttt{append} adds two already-rounded integers and the result's constructor round-trips an integer-valued cent amount back to the same integer (\texttt{round} of an exact or near-exact integer is a no-op up to floating-point noise far below one cent). Integer addition over $\mathbb{Z}$ is associative, so $c\big((a\oplus b)\oplus c\big) = c(a)+c(b)+c(c) = c\big(a\oplus(b\oplus c)\big)$ for \emph{all} $a,b,c$, not just the reported triple; since \texttt{costEur} is a deterministic function of \texttt{costCents} ($\mathrm{costEur}=c/100$), the two groupings also agree on \texttt{costEur}. No step in the computation rounds a value that has already absorbed a previous rounding, which is exactly what made the original version order-dependent.

\subsection{Free Category $F(G)$: Composition Failures Were Swallowed}\label{sec:bug3}

In the free category $F(G)$ induced by the travel graph, \texttt{FreeCategoryPath::compose} already returns an \texttt{Either}: \texttt{Right} on success, \texttt{Left} when the target vertex of the current path does not match the source vertex of the next edge (the paths do not form a connected walk). \texttt{Itinerary::advance()}, however, used that result incorrectly:
\begin{lstlisting}[caption={Original \texttt{Itinerary::advance} -- Left is discarded}]
$composed = $newPath->compose(FreeCategoryPath::fromEdge($graphEdge));
if ($composed->isRight()) {
    $newPath = $composed->getValue();
}
// execution continues either way
\end{lstlisting}
When composition fails, the \texttt{if} is simply not entered and \texttt{\$newPath} keeps its previous value; \texttt{advance()} still returns a brand-new, successful \texttt{Itinerary}. The categorical error is computed correctly and then thrown away, so an itinerary whose graph path is not actually a connected walk in $F(G)$ is reported as valid.

\textbf{Fix.} Propagate the failure instead of absorbing it:
\begin{lstlisting}[caption={Fixed \texttt{Itinerary::advance} -- Left fails the computation}]
$composed = $newPath->compose(FreeCategoryPath::fromEdge($graphEdge));
if (!$composed->isRight()) {
    $err = $composed->getValue();
    throw new RuntimeException("{$err['title']}: {$err['msg']}");
}
$newPath = $composed->getValue();
\end{lstlisting}

\textbf{Correctness argument.} After the fix, every execution path through the modified branch either (a) returns normally with \texttt{\$newPath} bound to the \texttt{Right} value of \texttt{compose} -- a path that is, by the definition of \texttt{compose}, a genuine morphism of $F(G)$ from the itinerary's start vertex to the new edge's target -- or (b) throws, and no \texttt{Itinerary} is constructed at all. There is no longer a third outcome where the method returns successfully with a path that \texttt{compose} itself rejected. A non-composable edge is an internal invariant violation of the step-building pipeline (every edge is constructed by the application itself from the previous step's state), not a user-facing validation outcome like a late flight or an over-budget trip, so failing fast with an exception is the appropriate signal, consistent with how every other \texttt{Left} produced inside this pipeline is already treated as a short-circuit.

\subsection{Regression Coverage}\label{sec:coverage}

Each fix above is paired with one new assertion in \texttt{tests/category\_laws\_test.php}, reproducing Prof.~Grinis' exact examples: \texttt{Some(false)} round-tripping through \texttt{bind(Option::pure)}; the $a=0.004,\,b=0.004,\,c=0.005$ monoid grouping; and a two-step \texttt{Itinerary::advance()} call with a deliberately mismatched edge, asserting that it throws. The full code of all three assertions is reproduced in Appendix~\ref{app:tests}, and running \texttt{php tests/category\_laws\_test.php} against the corrected code confirms all three now pass. Separately, the project's additional invariant suite, \texttt{LietuvaTravel\_regression\_checks.php}, exercises the \texttt{Option} monad, the \texttt{TripMetrics} monoid, and the free-category path/itinerary machinery under further edge-case inputs (nulls, sparse arrays, mismatched graph edges) and reports \textbf{10/10} checks passing.

\sectionWithoutNumber{Future Work}{future}{}
Beyond the three fixes above, two concrete follow-ups would further harden this codebase's categorical guarantees. First, the remaining ad hoc \texttt{InvalidArgumentException} checks inside \texttt{Some::bind} and \texttt{Right::bind} (``must return an Option/Either instance'') are runtime guards against a mistake the type system could catch instead; PHP's lack of higher-kinded types makes a fully static alternative awkward, but a static-analysis baseline (e.g.\ Psalm or PHPStan with a custom plugin recognising the Kleisli-arrow shape) could flag a non-conforming callback at the call site rather than at the moment it executes. Second, the law suite itself tests fixed, hand-picked values; a property-based layer (generating random floats, booleans, and graph shapes, and checking each law automatically over hundreds of generated cases per run) would very likely have caught \texttt{Option::pure(false)} and the sub-cent monoid rounding without waiting for a human reviewer to supply the exact counter-example, and is the most direct way to prevent a fourth such defect from reaching review.
